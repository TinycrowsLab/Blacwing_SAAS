# Console strings and i18n

Status: English only (v1). Owner: console (apps/web). Issue #272. Standard: CONTEXT_PACK §5 ("`next-intl`-ready strings, English only v1").

## Where strings live

- `apps/web/src/messages/en.json` is the English catalogue. It is flat, with dotted, namespaced keys: `common.*`, `nav.section.*`, `nav.item.*`, `breadcrumb.*`.
- `apps/web/src/lib/i18n.ts` is the accessor. `t(key, params?)` takes only catalogue keys (`MessageKey`), so a missing key fails `pnpm --filter @blackwing/web typecheck`.
- Shell components (`apps/web/src/components/shell/**`) render no literal user-facing text. The ESLint rule `blackwing/no-literal-ui-strings` (`scripts/eslint-rules/no-literal-ui-strings.mjs`) flags bare JSX text, string-literal children, and literal `aria-label`, `aria-description`, `title`, `alt` or `placeholder` values.

## Adding a string

1. Add the key to `en.json` in the namespace of the feature, for example `runs.empty.title`.
2. Render it with `t('runs.empty.title')`. Use `t(key, { name })` for `{name}` placeholders.
3. Type-check: an unknown key is an error, not a blank label.

Feature epics add their own keys; the shell only owns `common`, `nav`, `breadcrumb` and `toast`.

## Runtime behaviour

- Missing key (reachable only through an unchecked cast): `t` returns the key name, so the gap is visible in development. It logs nothing: `no-console` is an error in `apps/web`, and the typed `MessageKey` catches the mistake at compile time.
- Placeholder without a param: the `{name}` text stays visible, so the gap is obvious.
- Param values are inserted as text. They are never parsed as markup or as `String.replace` patterns.
- Dates and numbers: use `formatDate` and `formatNumber` (`Intl`, locale `DEFAULT_LOCALE = 'en'`). Do not build dates or numbers by string concatenation.

## Format and future languages

- Messages are ICU-compatible. v1 uses only `{name}` interpolation. Plurals must use ICU `{count, plural, one {...} other {...}}` once a second language is added. Do not hand-pick `count === 1` in code.
- Layouts must not assume English length. Translated strings are often longer; feature epics should allow truncation and wrapping.

## Migration to next-intl

The keys do not change when `next-intl` lands:

1. Add the `next-intl` provider in `apps/web/src/app/providers.tsx`, loading `messages` for the active locale.
2. Move `en.json` to `messages/<locale>.json` per locale, keeping the same keys.
3. Replace the body of `t()` with the `next-intl` lookup. Keep `MessageKey` derived from `en.json`, so the type check still holds.
4. Date and number helpers switch their locale from `DEFAULT_LOCALE` to the request locale.

## Out of scope for v1

- Translating any string. Only the English catalogue exists.
- Empty-state and feature copy (`lib/empty-states.ts`, feature pages). Those move into the catalogue as their epics land. Form toasts already use `toast.*` keys.
