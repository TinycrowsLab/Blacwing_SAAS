Blackwing platform threat model

This is the shared picture of what Blackwing defends, from whom, and by which deterministic mechanism. It covers the platform as a system: trust boundaries, data flows, assets, adversaries, the threats at each boundary (STRIDE), the mitigation for each threat, the §8 invariant it relies on, and the epic that owns it. It also records the residual risks and the sign-off status.

It is a living document (see Change procedure). It grounds the invariant matrix (SECREVIEW-002) and the abuse tests (SECREVIEW-003 and SECREVIEW-004). The automated tests themselves, and infrastructure controls (INFRA), are out of scope here.

Normative sources: CONTEXT_PACK §3 (architecture), §4.1 (sandbox and egress topology), §4.5 (policy and prompt injection), §7 (domain) and §8 (invariants).

Note

the threat model describes the target design. Each mitigation is owned by an epic. Whether a mitigation is built yet is tracked by that epic's issues, not by this page.

1. The two highest-stakes properties

1.1 Target content is untrusted, and enforcement never depends on the model

Every byte that comes from a target is untrusted data: HTTP bodies, HTML, JavaScript, source code, DNS records, certificate transparency entries, archived pages and OSINT material. An attacker who controls a target can put instructions in that content to steer the agent (prompt injection, §4.5).

The model is never a control (§8.11). Each safety property is enforced by deterministic code that sits outside the model:

  • the PreToolUse hook, which asks the policy decision point (PDP) before every Bash command and every target-interaction tool call;
  • the egress gateway, which decides every target connection, DNS answer and redirect;
  • the request, time and cost budgets;
  • the kill switch and the envelope expiry;
  • the destructive-class hard block, the reversal-journal precondition and the separation-of-duties check.

A prompt-injected agent can ask for anything. The only thing it can do is send requests through the controls above, and those controls decide the outcome without reading the model's intent.

1.2 The platform must not attack itself or third parties outside authorisation

Blackwing sends real traffic. Two failure modes are unacceptable:

  • Attacking itself. A sandbox or a target reaches Blackwing infrastructure: the control plane, the data stores, the cloud metadata endpoint, or another run's sandbox (SSRF of our own infrastructure).
  • Attacking third parties. Traffic reaches a host that is not in a verified asset, not in the standing authorisation's scope, outside the test window, outside the envelope, or in the destructive class.

Deterministic controls that prevent both:

Control Mechanism Invariant
Ownership verification An unverified asset cannot be targeted (DNS TXT, HTTP file or manual letter). §8.10
Signed envelope Target traffic needs a signature-verified, unexpired envelope. Expiry mid-run blocks at once. §8.1
Scope rules and private-range block Include and exclude rules are enforced on hosts, paths, ports and methods. Private, link-local and metadata ranges are blocked unless explicitly in scope. §8.2
Destructive class blocked The baseline policy hard-blocks the destructive class. state_changing needs an approved SA, Gate 1 and a journal entry. §8.3
Egress network policy The sandbox has three allowed destinations (§1.2.1 below). All other traffic is denied at the network layer. §8.2
Budgets and kill Request, rate and cost budgets per test case. The kill switch stops everything in scope. §8.5

1.2.1 Sandbox egress: three destinations only

Every agent sandbox (§4.1) may reach exactly three destinations. All other egress is denied (Kubernetes NetworkPolicy plus host firewall):

  1. the egress gateway, for target traffic;
  2. the model gateway, for Claude, with a per-session virtual key;
  3. the Run Broker API (/internal/broker/*), for tool backends, with a run-scoped token.

Not reachable from a sandbox: the internet, the cloud metadata endpoint (169.254.169.254), the host Docker socket, other runs, and the platform's own control plane.

4. Adversary catalogue

ID Adversary Capability Goal Boundaries they reach
ADV-1 External attacker Internet access, no account Steal tenant data, take over accounts, abuse the platform for attacks TB-1, TB-2
ADV-2 Malicious or curious tenant user Valid account in one tenant, may hold admin or developer role Read other tenants' data, target assets they do not own, bypass approvals TB-2, TB-3, TB-8, TB-10
ADV-3 Compromised or prompt-injected agent session Controls the content the agent reads (a target's HTTP, DOM, source or DNS). Can issue any tool call. Reach out-of-scope hosts, the platform itself or other tenants; forge findings; exfiltrate secrets TB-5, TB-6, TB-7, TB-8
ADV-4 Malicious insider or rogue platform operator Platform operator access (see §1.2 of the pack), infrastructure access Read tenant data, alter audit history, flip kill or release state, change policy TB-4, TB-9
ADV-5 Supply-chain attacker Compromises a dependency, build step, image, or an upstream binary (SDK, Claude Code, tool) Run malicious code in the platform or in every sandbox TB-11
ADV-6 Curious cross-tenant tenant A tenant with its own legitimate use, probing for side channels Infer another tenant's assets, findings or activity from timing, shared caches or shared infrastructure TB-8

ADV-3 is the case the platform is built around. It has no account and no trust. The agent is a tool that an adversary who controls target content can steer.

8. Gaps and non-mitigations

These are recorded as gaps and are not counted as controls.

  • "The model will refuse." A refusal is not a control (§8.11). Refusals are recorded as model_declined for coverage and for the eval harness only (§4.4).
  • "The system prompt says stay in scope." The signed authorisation context in the system prompt is a statement to the agent, not an enforcement point (§4.5). The gateway and the PDP enforce scope.
  • "The persona is told not to use the network." Persona allowlists and disallowedTools are defence in depth. The network policy and the gateway enforce it.
  • Model-written findings. A finding written by an agent is a candidate. Only the validator confirms it, and a human releases it.
  • Target-side defences. A target that blocks the agent is not a Blackwing control. Blackwing must not depend on targets behaving well.

9. Change procedure

  • A pull request that adds or changes a component, a trust boundary, a data flow or an adversary updates this page in the same change. The PR template carries this checklist item.
  • Each new threat gets an ID (T-nn), a deterministic mitigation, a §8 invariant and an owner epic. A threat with no deterministic mitigation becomes a residual risk (section 7) with an owner, or a fail-closed gap (section 8).
  • Each residual risk keeps its owner and acceptance status. Changing the status needs a second engineer's review.
  • A change to this page is reviewed under the same separation-of-duties rule as other security decisions.
