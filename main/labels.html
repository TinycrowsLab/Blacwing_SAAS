Label catalogue

Every GitHub label in this repository is defined in .github/labels.yml. That file is the single source of truth: change labels there, never in the GitHub UI. This page explains when to apply each group. The tables at the end are generated from the file.

How labels are applied

A planned issue (written to CONTEXT_PACK §11) carries these labels:

Group How many Rule
type:* exactly 1 type:task for a PR-sized unit, type:epic for an epic's parent issue, type:spike for a time-boxed investigation. Bug reports carry bug instead.
priority:* exactly 1 on tasks and epics P0 is needed for the first end-to-end grey-box run, P1 is a v1 must-have, P2 a v1 should-have, P3 nice-to-have or Later.
size:* exactly 1 on tasks XS < 2 h, S ≤ 0.5 d, M ≤ 1 d, L ≤ 2 d. There is no XL: split the issue.
area:* exactly 1 on tasks and epics The epic's Area in EPICS.md.
epic:* exactly 1 on tasks and epics The epic key in EPICS.md. A task's key starts with it (EGRESS-004 → epic:EGRESS).
Functional (security, gate, agent, infra) 0 or more Apply each one the change touches. security means a §8 invariant or a security-owned path (code owners) is involved, and the PR needs security review.
Feature (F1 … F44) 0 or more Each feature from FEATURE_LIST.md the issue implements.
Workflow 0 or more v1 / later for release scope. discovered for work raised while building another issue. online-porting + offline-stub for work that used a local substitute and must be ported online before go-live.
GitHub defaults as needed bug (set by the bug template), duplicate, invalid, wontfix, question and so on for triage.

The issue templates ask for the key, epic, area, priority, size, features and dependencies. Issue forms can only set fixed labels, so the Task template sets type:task and the Bug template sets bug. Whoever triages the issue applies the other labels from those fields. Each dropdown in the templates lists exactly the values of its label group, and scripts/check-github.mjs fails when they drift apart.

Changing labels

  1. Edit .github/labels.yml. Names are unique ignoring case (GitHub compares label names case-insensitively), at most 50 characters, with no commas. Colors are 6 hex digits without #, quoted (an unquoted 000000 would be read as a number). Descriptions are 1-100 characters. A label in a group with a prefix must start with it.

  2. Renaming: change name and add the old name under previously:. The sync then renames the label in place, so every issue keeps it, instead of creating a second label. Remove the previously: entry once the rename has been applied.

  3. Regenerate the tables on this page with node scripts/sync-labels.mjs --write-docs. pnpm labels:check (and pnpm test) fail while this page is out of date.

  4. Preview the change against the live labels without touching them:

    gh label list --repo TinycrowsLab/Blacwing_SAAS --json name,color,description --limit 500 > /tmp/labels.json
node scripts/sync-labels.mjs --dry-run --current /tmp/labels.json

The sync script

scripts/sync-labels.mjs validates the catalogue and reconciles a repository's labels with it. The CI label-sync job (#844) runs it. It is idempotent: a second run right after a successful one changes nothing.

Command Does
node scripts/sync-labels.mjs --dry-run Validates the catalogue and lists every label. Writes nothing.
… --dry-run --current <file.json> Also prints the diff against a snapshot (gh label list --json name,color,description format).
… --dry-run --repo OWNER/NAME Reads the live labels through the GitHub API (GITHUB_TOKEN or GH_TOKEN) and prints the diff.
… --repo OWNER/NAME Applies the diff, then re-reads the labels and fails unless nothing is left to change.
--prune Also deletes labels that are not in the catalogue. Without it they are reported as extra and kept.
--fail-on-diff Exits 1 when the diff is not empty (drift check).
--json Prints a machine-readable report.
--write-docs / --check-docs Regenerates / checks the tables below.

The diff lists each label as create, update (color, description or a case-only name change), rename (found under a previously: name), delete (only with --prune), unchanged or extra. If a label and one of its previous names both exist, the script updates the label, keeps the old one and prints a warning, because the old label's issues have to be moved by hand first. A failed API call stops the run and reports what was applied already. Re-running continues from there, because the diff is recomputed each time. The token is only sent in the Authorization header and never printed.
